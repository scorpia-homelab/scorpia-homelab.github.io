Two engines, one night: upgrading both LLM servers on our AI box

4 November 2026 · Peter + Hermes Agent · window: 3–4 Nov overnight
TL;DR — In a single overnight window we cut both LLM engines on our AI server up to new versions: the Strata server (engine 0.1.48 → 0.1.55) and the vLLM XPU service (v0.32.0 → v0.33.0). Both survived gate checks, canary batteries and full benchmark re-runs. Quality scores came out identical, decode speed moved +2.7% on one engine and was a statistical wash on the other — and we accidentally disproved a crash we had been working around for six weeks.

The setup: one server, two engines, one agent

Our AI server carries two GPUs and two inference engines, and they are load-bearing in different ways:

  • Strata (RTX 3080 Ti) serves Qwen3.8-Flash-Next IQ3_S — this is the model powering the lab’s main agent chat. Upgrading it means upgrading the LLM that runs the agent’s own turns, which is a self-preservation problem as much as an ops one.
  • vLLM XPU (Intel Arc Pro B70 32 GB) serves Qwen3.8-27B GPTQ-Int4 with MTP speculative decoding as the auxiliary heavier model.

Because the engines share a box but never share a GPU, one can restart while the other keeps the agent alive — the rule for the night was that the two restarts must never overlap.

Engine 1 — Strata 0.1.48 → 0.1.55

The Strata upgrade was scripted as a gated cutover: download the staged components, verify them against the signed component manifest, stop nothing until every pre-gate passes, swap the engine, then re-run banner checks, a 16-flag config gate, and a live generation probe before declaring success. A state file records the outcome so the benchmark and publish steps downstream only fire on a clean cutover.

First attempt: aborted, and that’s the system working

The scheduled 03:00 cutover aborted pre-flight without touching production. Digging in found three genuine bugs — in our automation, not the upgrade:

  1. Silent copy failure. The AI server’s SFTP subsystem is broken, so the scp that stages the installer fails quietly (exit 1, zero output). Nothing landed, the gate correctly refused to proceed. Fix: stage files via ssh ‘cat > file’.
  2. Watchdog false alarm. A companion watchdog conflated “staged file missing” with “host unreachable” and shouted about an outage that never happened — the server never went down, clean journal across the whole window.
  3. Self-referential SHA gate. The installer’s integrity pre-gate hashed the component manifest and then grepped for that hash inside the same manifest — structurally unable to pass. A latent bug that would have blocked every future upgrade.

With all three fixed, the cutover ran under supervision at ~11:03 the next morning: CUTOVER_OK — engine 0.1.55 live, all 16 config-flag gates green, generation probe passed. Chat was down roughly one minute; the agent’s next turn already ran on the new engine. (One extra wrinkle: the official updater script returned success but didn’t actually swap the engine — the staged-file fallback did the real work, which is exactly why that fallback exists.)

Engine 2 — vLLM XPU v0.32.0 → v0.33.0

The B70 service is pinned to an exact image digest (v0.32.0), and a small cron watchdog flags any newer vllm-openai-xpu release. v0.33.0 landed on 2 November, so the upgrade window ran 01:00–01:25 with a hard 02:15 deadline.

Gate first: does the new image even run our patches?

This deployment carries two hotfix patches against vLLM internals (MTP drafting and a boundary fix in the gated-delta-net attention backend). Before touching production, the new image was booted in a throwaway container with the patches mounted read-only — no GPU work, no downtime: 

===GATE1-PATCHES===
patched .../vllm/model_executor/models/qwen3_5_mtp.py
anchor matched: v0.32            # boundary file unchanged v0.32 → v0.33; dual-anchor held
patched .../vllm/v1/attention/backends/gdn_attn.py
===GATE2-IMPORTS===
vllm 0.33.0                      # imports clean
===GATE3-FLAGS===
reasoning_parser True · speculative_config True · mamba_cache_mode True ...

The boundary patch is written with anchors for both v0.32 and v0.33 precisely so an image upgrade shows up as a clean gate result rather than a mystery failure at boot. It did its job.

Cutover and A/B: the speed picture

Script backed up, digest swapped, service restarted: healthy in ~130 s, zero restart loops. Then a fair test — the same speed probe run on both images in the same window, so thermals and background load can’t rig the comparison:

v0.33.0v0.32.0 (same night)
Single-stream decode (mean of probe runs)46.4 tok/s46.6 tok/s
Difference0.4% — a statistical wash, well inside tolerance
Canary battery (arithmetic, JSON schema, code syntax, prose)4/4 PASS4/4 PASS
MTP draft acceptance rate2.58–4.212.47–2.68

Decision rule: keep the new image if it is within 10% and quality gates stay green. It cleared that easily, and the speculative-decoding acceptance rate actually looks better. Both images landed slightly under the documented 49–53 tok/s band on the night — identical on both, package temperature was 58 °C during runs, so we call it thermal rather than version-related.

The surprise: a six-week-old crash that turned out to be a ghost

Since v0.27 we have run this service with --max-num-seqs 1 — a single request at a time — because combining that pin with MTP speculative decoding and concurrent streams reliably corrupted output on the Intel XPU path. The upstream fix (vLLM PR #54931, mixed spec/non-spec batches in GDN attention) was closed unmerged in September, so the pin was documented as “dead in every current release.”

As part of the upgrade study we ran a falsification test on v0.33 in a separate test container: two streams against one model, then deliberately staggered three streams so new prefills landed mid-decode — the exact pattern that used to trigger the bad mixed batch. Result: 43.6 + 40.0 tok/s concurrently (80.1 aggregate), zero errors, engine healthy afterwards, acceptance rates normal. Something else in v0.33’s GDN path evidently fixed the mix even though the named PR never merged.

Discipline point, though: we did not lift the seqs=1 pin in production on the strength of one clean test. A silent-corruption failure mode earns a full corruption battery plus a long soak before a pin comes off. The pin stays until then — but the “impossible” is now on the table.

One more thing we measured that week

While we were at it, the B70’s 27B benchmark row was re-run with the reasoning parser enabled (--reasoning-parser qwen3) so thinking tokens are counted separately instead of leaking into answer text. Composite went 8.5 → 9.8 with the same tests, 76,251 thinking tokens measured across the suite, and 60.4 tok/s on the speed test. The honest-failure badge on one test stayed — the harness records capacity failures rather than hiding them. Row: qwen3.8-27b-gptq-int4-b70-vllm-rp.

What the night actually bought us

  • No quality regression on either engine — that was the bar, and benchmark re-runs rather than vibes are what clear it.
  • A small speed bump on the main chat engine (+2.7%), a wash on the 27B engine — and we can say that confidently because the A/B ran in the same thermal window.
  • Three automation bugs caught by the safety design itself — every failed upgrade attempt aborted before touching production. The gate did its job even when the gate’s own plumbing was broken.
  • A pinned limitation demoted from “fact” to “candidate” — with the production workaround left safely in place.
